# Design audit + canonical token set (M8b.1)

Audited 2026-09-06 against `main` at `6c24af3`. This is the second half of the pre-polish research:
[ui-design-direction.md](ui-design-direction.md) (M8b.0) surveyed the design skills in this
environment, ran the review-shaped ones against the renderer, studied Helium's patch set and set the
direction. **That inventory is not repeated here — it is cited.** This document does the two things
M8b.0 left to M8b.1: an **audit with counts and `file:line` citations** a reader can check, and the
**canonical token set** that M8b.2 lands and the M8b.3 fan-out converges on.

Every number below is regenerated by one committed script:

```bash
node scripts/design-inventory.mjs             # §2 — every utility and literal, by category, with file:line
node scripts/design-inventory.mjs --contrast  # §3 — WCAG ratios for the 80 fg/bg pairs the app renders, light and dark
node scripts/design-inventory.mjs --proposed  # §5 — the same check over the canonical set (63 pairs, 0 failing)
```

Line numbers are exact for `main@6c24af3`. §2's citations come straight from the script; the `sites`
column in §3 and the citations in §4 are hand-typed against the same commit (each was re-verified in
review), so once the M8b.3 sweep begins, re-run the script for live numbers and read the prose
citations as historical.

The **`dark:` variant count is 180**, against 482 colour uses. M8b.0 §5.1 explains why: `chrome-*`

remove the mechanism, not just the instances.

### 2.3 Radius — 6 spellings, 72 uses → 4 values

`rounded` ×42, `rounded-full` ×12, `rounded-lg` ×7, `rounded-md` ×6, `rounded-t` ×3, `rounded-sm` ×2.
In Tailwind v4 `rounded` and `rounded-sm` are both `0.25rem`, so `ThumbnailRail.tsx:159` (`rounded`)
and `:165` (`rounded-sm`) paint the same corner while reading as different in source; `FormatBar.tsx:102`
is the other `rounded-sm`. Effective ramp: **4px** (47 uses: controls, chips, bubbles' badges, menu),
**6px** (6 uses, all `ExportPptxDialog` + `AuthTab` cards), **8px** (7 uses: chat bubbles, arrange bar,
both dialogs), **pill** (12 uses: context chips, HUD pills, present controls, budget bar, rotate handle).

Inconsistencies: chat bubbles are 8px (`ChatPanel.tsx:225–257`) while the auth card in the same
column is 4px (`:305`); the arrange bar (a floating toolbar) is 8px (`ArrangeBar.tsx:145`) while the
context menu (a floating menu) is 4px (`SlideContextMenu.tsx:139`); the dialog is 8px and its inner
tabs `rounded-t` 4px with a `border-b-2` underline (`SettingsDialog.tsx:175`) — concentric radius
(`outer = inner + padding`) holds nowhere. Ceiling is 8px everywhere, which matches Helium's `kMSmall`
7 / dialogs 8 (M8b.0 §4.1); no chrome pill exists except genuine chips and the HUD. **Keep the ceiling;
name the three steps.**

### 2.4 Shadow — 5 spellings, 7 uses

`shadow-sm` (`ThumbnailRail.tsx:165`), `shadow-md` (`ArrangeBar.tsx:145`), `shadow-lg`
(`SlideContextMenu.tsx:139`, `PresentControls.tsx:47`), `shadow-xl` (`SettingsDialog.tsx:146`,
`ExportPptxDialog.tsx:69`), and the bespoke `shadow-[0_1px_2px_rgba(0,0,0,0.12),0_8px_24px_rgba(0,0,0,0.10)]`
on the canvas slide (`SlideCanvas.tsx:123`) — the only two raw `rgba()` literals in a component.
Every value is black-alpha and none is redefined for dark, so on the `#1f1f22` ground they are
invisible and separation falls back to the 1.24:1 hairline. Three of the five sit on elements that
**also** carry a hairline border (thumbnail, arrange bar, menu, dialog) — the "border and floating
shadow on the same element" pattern every source in M8b.0 §4.2 rejects.

### 2.6 Borders and outlines — 15 width spellings, 2 styles

`border` (1px) ×42 with side variants ×14; `border-2` on the selection box and editing frame,
`border-y-2`/`border-t-accent` for the drop indicator, `border-b-2` for the settings tab underline;
`outline outline-1` on the canvas slide (chosen over `border` so it does not affect layout —
`SlideCanvas.tsx:123`, keep); `ring-1` on the selected thumbnail plus `ring-2 ring-offset-1` on its
focus (`ThumbnailRail.tsx:159/167`) — the offset has no colour, resolves to Tailwind's `#fff`, and
paints a white halo on the dark rail (M8b.0 §2.5e; still shipped). `border-dashed` ×6 marks four
different things: hover outline, multi-select box, editing frame, "+ New" and empty-chip affordances.

**`outline-none` ×5**: `ThumbnailRail.tsx:159` and `DesignModeToggle.tsx:47` restore a
`focus-visible` ring; `ChatPanel.tsx:141` and `PropertyPanel.tsx:334` replace it with
`focus:border-accent` (a 1px colour swap — 2.91:1 in dark, §3); `SelectionOverlay.tsx:758` and
`SettingsDialog.tsx:146` restore nothing. Every other interactive element (≈40) relies on the UA
default, which Chromium draws in `-webkit-focus-ring-color` — a blue that is nowhere in the palette.

### 2.7 Motion — 4 utilities, 14 uses

`transition-colors` ×10, `transition-opacity` ×2 (`ChatPanel.tsx:198`, `PresentControls.tsx:42`),
`duration-300` ×1 (`PresentControls.tsx:42`), `animate-pulse` ×1 (`ChatPanel.tsx:274`). No `ease-*`,
so all ten colour transitions run on Tailwind's default `150ms cubic-bezier(0.4, 0, 0.2, 1)` — an
ease-in-out on state feedback that `emil-design-eng` and M8b.0 §5.5 both want instant-in. The pulse
is a 2s loop with no `prefers-reduced-motion` guard; the renderer contains that media query zero
times. M8b.0 §3.1 F1–F7 stand unchanged and are not repeated.

### 2.8 Opacity, z-index, blur

**Opacity** (8 spellings, 18 uses): disabled state is `opacity-30` (present controls), `opacity-40`
(arrange bar, send button), `opacity-50` (eight settings controls + property fields), `opacity-60`
(composer) — **four disabled opacities**. Also `opacity-40` for the dragged thumbnail, `hover:opacity-90`
on the send button, `opacity-50`/`opacity-80` on breadcrumb text (`SelectionOverlay.tsx:894/895`) —
the last two are text colour done with opacity, which composites unpredictably over the HUD.

**Z-index**: `z-50` claimed by four independent surfaces (`SlideContextMenu.tsx:139`,
`ExportPptxDialog.tsx:61`, `PresentSurface.tsx:154`, `SettingsDialog.tsx:134`); `z-10` by the arrange
bar and the present blanker. No ordering contract: opening Settings from the menu bar while a context
menu is open is decided by DOM order.

**Blur**: `backdrop-blur` (8px) on the arrange bar and present controls — the two floating HUDs; fine,
and the one glassmorphism M8b.0 §8 permits.

## 3. Measured contrast

Method: WCAG 2.1 relative luminance from sRGB; Tailwind v4 palette colours converted from their
OKLCH definitions in `node_modules/tailwindcss/theme.css`; alpha layers composited in order over the
opaque ground they actually sit on. The composite grounds (all opaque results):

| Ground | Composition | Light | Dark |
| --- | --- | --- | --- |
| canvas mat | `canvas-mat/25` over `shell-bg` · `black/40` over `ink` (`SlideCanvas.tsx:96`) | `#d5d5d5` | `#131314` |
| property panel | `shell-bg/95` · `ink-alt/95` over the mat (`PropertyPanel.tsx:165`) | `#f1f1f1` | `#25252a` |
| dialog scrim | `black/40` over the app ground | `#929292` | `#131314` |
| HUD pill | `black/70` over a white slide · over `ink-alt` | `#4d4d4d` | `#0b0b0d` |
| arrange bar | `white/95` · `ink-alt/95` over the slide | `#ffffff` | `#26262b` |

Thresholds: **4.5:1** for text (nothing in the chrome reaches WCAG's 18.66px-bold "large" size),
**3:1** for UI components (WCAG 1.4.11). Disabled controls and `aria-hidden` decoration are exempt
and reported only in the script output. 80 pairs measured; the full table is `--contrast`. **25 fail.**

## 5. The canonical token set

### 5.1 Principles (decisions, each traceable to M8b.0)

1. **Extend, don't rename.** Of the 14 existing tokens, the 12 mode-bound ones (`shell-*`,
   `chrome-*`, `ink-*`, `canvas-mat`) keep their names and values until they are retired; `accent`
   keeps its name and light value and gains a dark one; `accent-soft` keeps its name and is re-valued
   (it has no consumers). New **role** tokens are added beside the 12; components migrate surface by surface in M8b.3; the legacy tokens
   are deleted in the last M8b.3 PR behind the two survivor checks in §5.4 — **not** behind
   `theme-tokens.test.ts` as shipped, which derives the namespaces it polices from the tokens still
   declared (by design, see its header) and therefore goes blind to a deleted namespace: deleting the
   12 `shell`/`chrome`/`ink`/`canvas-mat` declarations with the renderer untouched leaves 324
   references and a green run. This reaches M8b.0 §5.1's role-bound end state with no repo-wide
   rename and no merge-conflict machine.
2. **One role, one token, values swap by mode.** A role token is declared once in `@theme` with its
   light value and overridden in `@media (prefers-color-scheme: dark) { :root { … } }`. Tailwind emits
   `background-color: var(--color-surface)` (verified, §5.7), so the override reaches every utility
   and a component writes `bg-surface` with **no `dark:` variant**. Bare `:root` therefore carries the
   complete light palette and dark redefines only what changes — no colour has its only definition
   inside a media query (the existing convention, kept).
3. **One neutral family, both modes.** The shipped dark neutrals are a cool grey (`H ≈ 286`,
   `C 0.005–0.014`); the light neutrals are pure grey (`C = 0`). Helium's replacement neutral ramp is
   `oklch(0.48–0.83, 0.033, 279–282)` (computed from the hexes M8b.0 §4.1 quotes) — the same family.
   So the light neutrals take hue 286 at `C 0.002–0.006`, the dark values stay byte-identical, and
   `canvas` is the one achromatic token, so the mat never tints a slide's colours. Lightness of the
   light neutrals is kept where it was measured to work (`text` 0.222, `text-muted` 0.485, `surface`
   0.985, `line` 0.905 ≈ `chrome-line`'s 0.913).
4. **One base unit.** Tailwind's 4px `--spacing` is the base; every dimension token below is a multiple
   of it, including the 28px control (7 × 4) — Helium's `kToolbarButtonHeight` and our `h-7`. Type
   line-heights are 16 / 16 / 20 / 20 so an 11px caption in a `py-0.5` chip is 20px and a 13px label
   in a `py-1` control is 28px — the control height falls out of the type token.
5. **Ceilings, not menus.** Three radii (4 / 6 / 8) plus pill for chips and HUDs; three shadows; four
   type sizes; three weights; two easings; four durations. Tailwind's default scales for radius,
   shadow, text, weight, tracking, leading, ease and animate are **reset with `--*: initial`** so
   `rounded-xl`, `text-sm`, `font-bold`, `ease-in` and `animate-pulse` stop existing as utilities — the
   guard is the compiler, before M8b.4's test. The resets cannot remove numeric or static spellings:
   `leading-N` (spacing-based — `leading-4`, the app's most-used leading, still compiles),
   `duration-N`, `z-N`, `ease-linear`, `rounded-none`/`rounded-full`. Those are M8b.4's check (6).
6. **Semantic hues are status only.** `danger`, `warning`, `success` never touch chrome, selection or
   emphasis; each status also carries a word or icon. The editing frame gets `edit` (blue) and the
   guides `guide` (teal) so the warning amber and the future AI-pending violet
   (40-design-mode.md §"AI pending") each keep one meaning.
7. **Accent unchanged in light; lifted in dark.** `#c43e1c` = `oklch(0.554 0.176 34.8)` stays. Dark
   uses `oklch(0.670 0.176 34.8)` = `#ed6444` (M8b.0 §2.2's value, re-verified: 5.09 on `surface`,
   4.66 on `surface-raised`). Because a lifted accent is too light for white text (3.23:1), **`on-fill`
   is a role token** — white in light, near-black in dark — and the same token is the text on every
   saturated fill (`accent`, `danger`, `warning`, `success`, `edit`): 5.19–7.13 light, 5.83–10.6 dark.

**Rules the pairs table assumes** (M8b.4 can lint R1–R3; R4–R6 are review items):

- **R1** A role token never carries a `dark:` variant. `dark:` on a colour utility is a finding once its surface has migrated.
- **R2** Palette colours (`red-*`, `amber-*`, `neutral-*`, `fuchsia-*`, …) do not appear in components; `white`/`black` only through `hud`, `scrim`, `on-fill`.
- **R3** Alpha on a token (`accent/10`) is not a way to invent a colour; the one permitted alpha is `hud-fg/70` (secondary HUD text, 5.17:1 measured); the HUD hover is the `hud-strong` token, never `hud/85`.
- **R4** `accent` text never sits on `accent-soft` (3.87 in dark); an accent *icon or border* may (≥ 3.87).
- **R5** `text-muted` never sits on `canvas`; the mat is not a reading surface (empty states use `text`).
- **R6** The focus ring is `outline-2 outline-focus outline-offset-2` and nothing else; because of the offset its contrast partner is the surrounding surface, which is what the 4.10 / 3.51 / 4.28 rows measure.

### 5.5 Compatibility with the `.sloodge` deck theme (30-slide-format.md §4)

- **Different documents, different namespaces.** Deck tokens are `--sl-*` inside each slide's own
  iframe document; chrome tokens are `--color-*` in the renderer document. They cannot collide, and
  `wrapSlideHtml`/`frameScript` inject no chrome CSS variables into a slide.
- **Different palettes on purpose.** The chrome accent is warm (`34.8°`); the default deck accent in
  30-slide-format.md is cool (`#4c8dff` = `oklch(0.658 0.182 261)`). The Design Mode colour picker
  offers **deck** swatches (`theme-swatches.test.ts`), never chrome tokens; chrome never draws with
  `--sl-*`. The `edit` token (`262.9°`) is close in hue to that default deck accent — acceptable
  because `edit` appears only as a dashed 2px frame with a labelled chip and never as a fill the
  slide could be confused with; if a future default theme moves to blue-orange, revisit.
- **The mat is achromatic** (`canvas`, `C = 0`) so slide colours are judged against neutral grey, as
  in every image editor; that is the one place the "choose your neutrals" rule is deliberately broken.
- **Same English words, separate CSS**: the deck schema names `surface`, `border`, `ok`, `warn`,
  `danger` (`theme.json`, emitted as `--sl-color-*`); chrome names `surface`, `line`, `success`,
  `warning`, `danger` (`--color-*`). Different documents, different prefixes — no collision, and the
  fan-out must not "align" them: renaming either buys nothing and the deck schema is versioned.
- **Chart series**: `tokens.series[]` is a deck concern (M8b.0 §9 — validate with `dataviz`'s script
  in a later milestone); chrome defines no series colours.

are emitted.** A role token with no consumer at compile time is absent from that build's CSS, so the

`@theme` resolves properly at the first build that uses the token (verified) — but M8b.2 lands the
tokens before any surface adopts them, so declare the role block `@theme static { … }`: M8b.2's own
emitted CSS then carries the full role block, the PR is reviewable and diffable, and the dark
overrides have something to override in the build that introduces them.

## 6. Non-goals (carried from M8b.0 §8, plus what this audit adds)

- **No "make it roomier".** `h-7` = 28px = Helium's toolbar button; 11–13px chrome text measures 6.1:1+. The two dense-UI carve-outs in `better-layout` and `styleseed` apply. Nothing in §4 adds padding or height.
- **No repo-wide rename.** Legacy tokens stay declared until the last surface migrates; M8b.3 PRs touch only their own files.
- **No new light-mode look.** Light neutrals move by < 1 ΔE; dark neutrals do not move. A user comparing preview.2 to preview.3 should notice fixed contrast and consistent controls, not a recolour.
- **No per-role accents, no second accent.** One `accent`, disambiguated by shape and position (M8b.0 §5.0). `edit` and `guide` are Design-Mode overlay colours, never chrome.
- **No animation beyond M8b.0's four bridges.** Selection, drop indicator, property panel, context menu, canvas fit and toolbar press stay bare by policy.
- **No UI or motion dependency.** Everything above is CSS the installed Tailwind and Chromium 140 already provide.
- **No wider scales.** Four sizes, three weights, three radii, three shadows, four durations. `initial` resets make the unused Tailwind steps uncompilable.
- **Not in M8b at all** (recorded so no agent "fixes" them): the keyboard path for Design Mode and the 8px handles (M8c), the 508px-of-fixed-chrome collapse problem, the ribbon/inspector/chat command-surface question, RTL, the 9px→11px thumbnail label is the only text-size change.
- **Do not "fix" what review cleared**: `sr-only` credential labels, 20px swatches at 4px gap, the small chip `×`, the canvas `outline`.

## 9. What the existing guard covers, and what M8b.4 adds

`tests/unit/design/theme-tokens.test.ts` (PR #47) already fails when a colour utility names a
`--color-*` token that `theme.css` does not declare, across every declared namespace, through variants
and alpha suffixes. It does **not** see: palette colours (`bg-red-500` is a valid Tailwind colour),
raw literals (`rgba(…)`, `#hex`) in class strings or `style` props, arbitrary values (`text-[13px]`,
`w-[188px]`) and alpha suffixes on role tokens (`bg-accent/10` — rule R3 permits only `hud-fg/70`),
`dark:` variants on role tokens, or the 12 retired tokens once they are meant to be gone (never
`accent` / `accent-soft`, which are canonical). M8b.4's guard adds those five checks plus a sixth —
the spellings the `--*: initial` resets cannot remove: numeric `leading-N`, `duration-N`, `z-N`,
`ease-linear` — over `src/renderer/src/**/*.tsx`, with an explicit allow-list (`-mb-px`;
`max-w-[90vw]`-style viewport clamps on dialogs; the `slide://` URL strings that contain `#`), and
must red under each of seven mutations: reintroduce `text-[13px]`, `bg-red-500`, a raw `rgba()`
shadow, `dark:bg-ink-alt` on a migrated file, `bg-chrome` after the retired block is deleted,
`leading-4`, and `bg-accent/10`. `scripts/design-inventory.mjs`'s classifier is the starting point — it already separates
colour, arbitrary and palette spellings with citations.
