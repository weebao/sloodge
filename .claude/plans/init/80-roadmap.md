# 80 — Roadmap & PR Breakdown

Principles: every PR is incremental and digestible; titles prefixed `feat/fix/doc/chore/ci`; stacked with jj where dependent. CI = unit tests only — never compilation or packaging on the development path; the single exception is M9.0's release workflow, which fires on a `v*` tag and on nothing else (70-testing-ci.md §6.5). `chore`/config/init PRs auto-merge (`gh pr merge --auto`). Feature PR descriptions are one-liners. Perf/compilation PRs must include before/after logs or metrics. UI PRs include a recording **as an animated GIF** (GitHub renders GIFs inline in a PR body; webm/mp4 attach as unviewable files — do not produce them). See 70-testing-ci.md for the WSL/headless caveat; Playwright records webm, so convert it with ffmpeg and keep only the GIF (plus a PNG still).

| PR | Title | Notes |

| M3.6 | `feat: transform controls (stretch/zoom handles, rotate, flip H/V, duplicate)` | Handles on the selection box; rotation via corner handle with angle snap (0/45/90); flip = CSS transform written back to source; duplicate = Ctrl/⌘+D cloning the element subtree with fresh `data-sl-id`s. **Shipped in two PRs.** #27 landed the rotation handle, Flip H/V, `Ctrl/⌘+D` duplicate (fresh author `id`s and `data-sl-id`s through the whole clone, with intra-clone `href`/`url(#…)`/`for`/`aria-*` references repointed) and the rotated selection box; the stretch (edge) and zoom (corner, `Shift` = aspect) handles are M3.5's. The second PR closes what the row implied but #27 did not do, and records four decisions that differ from it. **Resize under rotation** works in the element's own axes: the pointer delta is turned into the box's frame, the axis-aligned resize runs there, and the box is re-placed so the anchored edge or corner stays fixed *on screen*; the grips' cursors turn with the box. **Snapping** is PowerPoint's model rather than #27's always-45° grid (which made a 30° tilt unreachable without a modifier): free by default, magnetic at multiples of 45° within 4°, `Shift` forces 15°, `Alt` bypasses the magnet; every commit is a whole degree read back from the source, so repeated drags cannot drift. **Composing with an author transform is loud, not lossy**: `inspectTransform` decomposes only `translate rotate scale` (single-axis aliases folded), each once, in canonical relative order; a `matrix()`, `skew()`, non-canonical order, repeated function or non-`deg` angle is *opaque* — the overlay hides the grips and the rotation handle, shows the reason in a badge, and the panel's Flip buttons carry it as a disabled tooltip. Move stays available on an element positioned with `left`/`top` (a drag there never touches the transform — `translateZ(0)`, the compositing idiom, must not make an element unmovable), and on anything whose transform decomposes, by writing a **leading** `translate()` that CSS applies last, in the parent's frame. An SVG child is not exempt from the rule as an earlier revision assumed: its `x`/`y` are geometry *inside* its own user space, so a screen-space delta written there under `rotate(30deg)` moves it ~34.6px right and ~20px down — it takes the `x`/`y` channel only when the transform leaves its axes parent-aligned, and the same leading-translate channel otherwise. Move is refused only where the transform cannot be decomposed at all, so neither channel can be shown safe. **Known gap:** the whole M3.6 transform stack reads and writes the *style* `transform` only, so an SVG element carrying the legacy `transform="rotate(30)"` **attribute** looks untransformed to the rotation handle, the flip, the duplicate nudge and this lock alike; closing that means teaching `readTransformShape`/`setStyleProp` the attribute form and is out of M3.6's scope. That refusal is the `refused` arm of **`moveChannel` in `buildFieldOps`**, the function that writes the bytes, not a check at each caller: enforced at the overlay alone it was found missing at the next entry point three rounds running (the group anchor, then align/distribute, then a source edit landing mid-drag), and enforced at `buildDragPatch` it was still missing from the panel's X/Y inputs, which reach `buildFieldOps` without passing through the drag. One `moveChannel` now answers "which channel does an X/Y edit use, and may it be written" for the reader, the writer and the message alike, so the panel field shown is by construction the field an edit would write, and the overlay's badge cannot describe a different rule from the one applied. Round 2's opaque-translate write path is subsumed by this and deleted rather than left unreachable. The panel's X/Y and the drag share one translate writer with the handles (`inspectTransform`/`composeTransform`), so a `translateX()` folds to one `translate()` rather than gaining a second and going opaque on its first drag. This reverses §5.3's "reorder to canonical and append unknowns verbatim", which kept the bytes but moved the element. A new translate is now *prepended* (`translate() rotate()`), the parent-space position, fixing an M3.3/M3.5 move that walked along a rotated element's own axis. **Flip** mirrors within the element's own frame (`scale` innermost, DrawingML's `flipH`-inside-`rot`): the tilt is kept, and text mirrors with the box — a notice says so, since CSS cannot flip a container and keep its glyphs readable. **Duplicate** folds the 16px nudge into a px translate, prepends a parent-space translate to an opaque one, and lands a non-px-translated clone (`-50%`, `1em`) in place with a notice naming the translate rather than writing `-34px` for `-50%`. The clone is freshened from a whole-document parse, not a fragment parse of its own bytes — a `<td>` outside a `<table>` does not survive the latter, which is how #27 duplicated a cell to two `id="a"` cells. |

| M8.5 | `perf: parse/source-map caching + incremental patching` | Cache parse5 source maps per slide-source hash; Design-Mode edits reuse spans instead of reparsing; agent edits patch single slides, never the whole deck (metrics required) |
| M8.6 | `perf: startup path audit` | Defer agent-SDK spawn, skill copy, and export modules off the critical path; V8 snapshot/lazy `require` where measurable; before/after startup traces in PR (metrics required) |
| M8.7 | `ci: perf regression check (local-runner report diffing)` | Perf suite runs locally (not on GitHub minutes); committed baseline JSON diffed by a fast CI job that only compares numbers — fails if median RAM ≥ 200 MB, startup or switch budgets regress >10% |
Every `perf:` PR must include the harness's before/after logs and metric tables in its description, per the PR conventions.

## Milestone 8b — Design polish pass (after every feature milestone; gates the release)
Everything up to here optimizes for *correctness*; this milestone is the one that optimizes for **how the app looks and feels**. It runs after M0–M8 are complete and before M9 cuts the release, because polish should ship in v0.0.1 rather than trail it.

| PR | Title | Notes |
|---|---|---|
| M8b.0 | `doc: UI design research` | User request: **research how to better design the UI before polishing it.** Use every design skill available in the environment (`apple-design`, `emil-design-eng`, the `interfaces:better-*` family — ui/layout/typography/colors/accessibility/writing/interface — `find-animation-opportunities`, `improve-animations`, `artifact-design`, `dataviz`), run the review-shaped ones against the shipped renderer, and research the internet for popular design languages and design-skill repos for apps like sloodge — including the [Helium browser](https://github.com/imputnet/helium) repo the user named, plus Linear/Raycast/Figma/Cursor-class desktop tools and PowerPoint/Keynote's own current chrome. Output: [research/ui-design-direction.md](research/ui-design-direction.md) — an opinionated design direction (OKLCH token set, spacing/radius/shadow/type/motion scales, ranked top-10 surface fixes, accessibility punch-list, explicit non-goals) that M8b.1–M8b.4 execute against |
| M8b.1 | `doc: design audit + token inventory` | **Explore what design skills/resources are actually available first** (the `artifact-design` and `dataviz` skills, any design system the environment exposes) and record what they prescribe — do not invent a house style from scratch if a vetted one is at hand. Then audit the shipped UI surface by surface (app shell, thumbnail rail, canvas, chat panel, property panel, arrange bar, export dialogs, present mode + its controls, first-run/no-key gate, notices/status lines) and inventory every color, spacing value, radius, shadow, font size/weight, border, and transition currently in use. Output: a written audit naming each inconsistency (the same "gray" spelled three ways, one-off paddings, ad-hoc `text-[13px]`), plus the **canonical token set** the polish will converge on — extending the existing `chrome-*`/`ink-*` Tailwind theme rather than replacing it, and staying compatible with the `.sloodge` deck theme tokens (30-slide-format.md) so app chrome and slide content don't fight. |
| M8b.2 | `feat: design tokens + primitives` | Land the canonical tokens (Tailwind theme extension + CSS variables) and a small set of shared primitives the surfaces will adopt — button variants, input, dialog/modal shell, panel header, toolbar group, chip/badge, status line. Light and dark must both be correct (the app already ships `dark:` variants; the audit will show where they've drifted). Accessibility is part of the definition of done: contrast ratios checked against WCAG AA for text and UI, visible focus rings on every interactive element, and no information conveyed by color alone. |
| M8b.3+ | `feat: polish <surface>` — **parallel subagents, one surface each** | Fan out one subagent per UI surface (rail, canvas/overlay, chat, property panel + arrange bar, export dialogs, present mode, menus/status bar), each converting its surface to the M8b.2 tokens and primitives, each its own reviewable PR with a before/after GIF. They run in parallel because the surfaces are independent once the tokens exist — that is exactly why M8b.1/M8b.2 come first: a fan-out without an agreed token set produces seven inconsistent opinions. Each PR must show it changed *only* presentation: no behavior change, existing tests unchanged and green, and the Design-Mode byte-span/undo invariants untouched. |
| M8b.4 | `test: visual consistency check` | A test that fails when a surface reintroduces an off-token value — e.g. scan the renderer's source for raw hex colors / arbitrary Tailwind values (`text-[13px]`, `p-[7px]`) outside the token definitions, with an explicit allow-list for genuine exceptions. Same discipline as the rest of the repo: the guard must red under a mutation that reintroduces a one-off value, or it is not a guard. |

## Milestone 9 — v0.0.1 release (gated on every other milestone reaching 100%)
**Preview cadence (user request 2026-08-01):** the user installs and hand-tests the GitHub release builds, and that is the only feedback channel into the real product — `v0.0.1-preview` was how "Design Mode is off by default" and "there is no inline text editing" surfaced after ~2,700 unit tests missed both. So **after every major batch of merged feature PRs (roughly every 3–5, or any user-visible behaviour change), publish a new pre-release** from `main`: bump the tag (`v0.0.1-preview.2`, `.3`, …), ship installer + portable zip, mark the previous preview superseded in its title, verify the bundle contains the new features' symbols before publishing (a stale build shipped once), and tell the user what changed. This is a standing convention, not a one-off PR.

When all milestones above are complete (every PR merged at review confidence 100, CI green) — **including the M8b design polish pass** — cut the first release.

**M9.0 is exempt from that gate and lands immediately.** It is release *infrastructure*, not a release step: it cannot fire until someone pushes a `v*` tag, so landing it early costs nothing and changes nothing about when the release happens. Landing it early is in fact the point — it has to exist before the first tag, or that tag gets hand-built and the whole failure mode it prevents happens one more time. Everything from M9.1 down remains gated.
| PR / step | What | Notes |
|---|---|---|
| M9.0 | `ci: release workflow (tag-triggered Windows build)` | `.github/workflows/release.yml` — push a `v*` tag, a `windows-latest` runner builds NSIS + zip from a **clean checkout of that tag** and attaches them to the release (draft-created if absent, so M9.4 keeps its human notes step). **Does not violate the unit-tests-only CI rule:** it is tag-triggered *only* — no `pull_request`, no `push: branches`, no `workflow_dispatch` — so it costs nothing during development and its bill is O(releases), not O(commits). Exists because a preview release was once hand-built from a stale worktree: the artifact predated a merged milestone, an entire export format silently did nothing in the shipped build, and no build step reported it. Hand-built artifacts have no provenance. `windows-latest` is load-bearing — NSIS cannot be built on Linux (electron-builder *executes* the installer to emit its uninstaller, needing Wine, which is broken on the WSL2 box), so the runner also retires the hand-synced duplicate builder config the manual procedure needed. The trigger set is asserted exhaustively by `tests/unit/packaging/release-workflow.test.ts`, whose YAML reader **fails closed** (any unmodelled line throws — an earlier revision could be walked past with a quoted key like `"pull_request":`), mutation-verified across 16 edits. Also ships two things the workflow cannot work without: a repo-root **`.gitattributes`** (`* text=auto eol=lf`) — without it `windows-latest` checks out CRLF and `pnpm test` reds before packaging is ever reached — and a **tag ↔ package.json version guard**, since `artifactName` interpolates the version and every tag would otherwise emit `sloodge-0.0.0-setup.exe`. See [70-testing-ci.md §6.5](70-testing-ci.md) and [docs/windows-smoke-runbook.md §8.5](../../../docs/windows-smoke-runbook.md) |
| M9.1 | `chore: electron-builder release config for v0.0.1` | Version bump to 0.0.1 — **this is now mandatory before tagging, not merely conventional**: M9.0's guard fails the job unless the tag is `v<package.json version>` (optionally `-<suffix>`, e.g. `v0.0.1-preview`). NSIS `.exe` installer + portable `.zip` for Windows; `.dmg` (plus `.zip` for auto-update) for macOS — dmg is the standard macOS distribution format. **Must also add `build/icon.png`** — `directories.buildResources` names a directory that does not exist, so every artifact (CI's included) currently ships the default Electron icon |
| M9.2 | Builds | **Windows: tag-triggered CI (M9.0), never by hand** — that is what produces the shipped `.exe` and `.zip`, from a clean checkout, with provenance. Local `electron-builder --win` remains the way to **debug** packaging (runbook §8), not the way to ship it. **macOS: still local**, on real hardware — `--mac` cannot be validly produced from Linux (`sips` is macOS-only, and the cross-built zips carry no `darwin` CLI). Unsigned; signing/notarization deferred past 0.0.1. A `macos-latest` CI job is deliberately *not* added: 10x billing for an artifact that is unsigned and untested anyway |
| M9.3 | Smoke-test runnability | The dev machine is Windows (WSL2): install and run the `.exe` on the Windows host and walk the v1 success path (new deck → generate → Design-Mode tweak → Present → export PDF/PPTX). macOS artifact is best-effort untested until a mac is available — state that plainly in the release notes |

The human step is what remains: upload the locally built `.dmg` and macOS `.zip`, write release notes summarizing milestones and known limitations (unsigned mac build, untested on macOS), and publish. Only reach for `gh release create` if the tag was pushed before M9.0 existed |

## Review gate (applies to every code PR)
Every code change is reviewed by a **fresh-memory subagent on Fable 5.1** (user directive 2026-08-01: all subagents — builders, reviewers, researchers — run on Fable) loaded with the repo-local [`ship-ready-review`](../../skills/ship-ready-review/SKILL.md) skill, given only the changeset. Before the first review round the branch gets a [`deslop`](../../skills/deslop/SKILL.md) pass — AI slop removed with behaviour proven unchanged by the full gate, never touching security boundaries or rationale comments. The change is fixed and re-reviewed until the verdict reaches **confidence 100 (zero blockers, zero majors, lint/typecheck/tests independently verified green)** before merge. Work done directly by the orchestrator without a subagent is held to the same bar: exhaustive self-verification plus a deslop pass.
